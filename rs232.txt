
rs232.js — Instruction Sheet
----------------------------

Purpose
-------
rs232.js is the virtual serial / RPC layer that mediates all communication between the privileged Qandy host (parent) and guest program runtimes (iframes, other transports). It serves as the canonical place to:
- forward keyboard/input events to guests,
- accept and validate guest requests for privileged operations,
- dispatch guest requests to registered host handlers (e.g., system/execute functions, dos.*),
- manage request/response lifecycle (IDs, timeouts),
- enforce permissions, quotas and logging.

This document lists public functions, variables, message formats and usage examples for implementers and integrators.

Terminology
-----------
- host: the privileged Qandy page (parent).
- guest: the untrusted program runtime (iframe or other transport).
- transport: the window.postMessage endpoint or other comms channel used to exchange messages.
- RPC: request/response with id (like JSON-RPC but minimal).

File: rs32.txt (this file) documents the API and message formats.

Public API (functions exported by rs232.js)
------------------------------------------

1) rs232.init(options)
   - Purpose: Initialize the rs232 subsystem.
   - Parameters:
     - options (object):
       - guestWindow (Window | null)       : (optional) initial guest iframe contentWindow
       - guestOrigin (string | '*')       : expected origin for guest messages
       - allowWildcardOrigin (boolean)    : optional, allow '*' origin (dev only)
       - defaultTimeoutMs (number)        : request timeout default in ms (default: 10000)
       - maxConcurrentRequests (number)   : concurrency cap (default: 32)
       - maxCommandsPerSecond (number)    : rate limit for guest->host requests
       - auditLogger (function)           : function(action, details) for logging (optional)
       - permissionChecker (async function(method, args, meta)) : optional hook to approve/deny
   - Returns: void
   - Notes: Must be called once early. Repeated calls reconfigure.

2) rs232.connectGuest(guestWindow, guestOrigin)
   - Purpose: Attach an active guest transport (iframe.contentWindow) and origin.
   - Parameters:
     - guestWindow (Window) : guest iframe contentWindow
     - guestOrigin (string) : expected origin of messages from guest (use '*' only for dev)
   - Returns: void
   - Side-effects: starts listening/forwarding for this guest.

3) rs232.disconnectGuest()
   - Purpose: Detach the current guest transport.
   - Returns: void

4) rs232.sendRequest(method, args, opts)
   - Purpose: Send a request to the guest and await reply (host -> guest).
   - Parameters:
     - method (string)       : method name (guest-facing)
     - args (array)          : array of arguments
     - opts (object, optional):
       - timeoutMs (number)
       - signal (AbortSignal)
   - Returns: Promise that resolves to result or rejects on error/timeout.
   - Example:
       const reply = await rs232.sendRequest('runCommand', ['foo']);

5) rs232.sendEvent(name, payload)
   - Purpose: Send a one-way event to guest (no reply expected).
   - Parameters:
     - name (string)
     - payload (any)
   - Returns: void

6) rs232.onRequest(handler)
   - Purpose: Register a handler function for guest->host requests.
   - Parameters:
     - handler (async function(req) -> res):
         req object: { id, method, args, meta }
         handler returns: { ok:true, result } or { ok:false, error }
   - Returns: subscription handle (object) or function to remove listener.
   - Notes: Multiple handlers may be registered; the first to return a non-undefined value wins.

7) rs232.forwardKey(keyEvent)
   - Purpose: Forward a normalized key event to the connected guest.
   - Parameters:
     - keyEvent (object):
         { type, code, key, altKey, ctrlKey, shiftKey, metaKey, repeat, timestamp }
   - Returns: boolean (true if forwarded)
   - Notes: This function enforces filters for privileged combos and relies on requestInputMode state (see below).

8) rs232.requestInputMode(mode, opts)
   - Purpose: Ask the host to grant or revoke a particular input mode for the guest.
   - Parameters:
     - mode (string) : 'line' | 'raw' | 'raw+pointer'
     - opts (object, optional):
         { requireUserGesture: boolean, timeoutMs: number }
   - Returns: Promise<{ ok: boolean, reason?:string }>
   - Notes: If 'raw' is requested a user confirmation must be presented before enabling and audit logged.

9) rs232.revokeInputMode()
   - Purpose: Revoke any granted raw input mode and restore the host's line mode.
   - Returns: void

10) rs232.setPermissionChecker(checkerFn)
    - Purpose: Replace or set the permission evaluator used for guest requests.
    - Parameters:
      - checkerFn (async function(method, args, meta) -> { allowed: boolean, prompt?:object })
    - Returns: void

11) rs232.auditLog(action, details)
    - Purpose: Write an audit entry (calls auditLogger if provided).
    - Parameters:
      - action (string)
      - details (object)
    - Returns: void

12) rs232.shutdown()
    - Purpose: Stop listeners, clear pending requests, and detach guest.
    - Returns: Promise when shutdown completes.

Public Variables / State (exposed or documented)
------------------------------------------------
- rs232.guestWindow    : current guest window (null if none)
- rs232.guestOrigin    : expected origin string
- rs232.pending        : internal Map of pending host->guest requests (id -> resolver)
- rs232.rpcId          : last used request id (incrementing)
- rs232.inputMode      : current input mode ('line'|'raw'|'raw+pointer')
- rs232.rawInputEnabled: boolean
- rs232.config         : the options passed to init()
- rs232.auditor        : audit logger function (if configured)
- rs232.permissionChecker : function used for permission decisions

Message formats (postMessage envelopes)
--------------------------------------
All messages share an envelope:
  { __qandy: true, type: <string>, payload: <any> }

Guest -> Host (common):
- type: 'guest.req'
  payload: { id: <number>, method: <string>, args: <array>, meta: <object?> }
  -> host must respond with host.res message for same id.

- type: 'guest.event'
  payload: { name: <string>, data: <any> }
  -> one-way event from guest to host.

- type: 'guest.input.key'
  payload: KeyEventObject (see below; used if parent forwards key events)

Host -> Guest:
- type: 'host.res'
  payload: { id: <number>, ok: true, result: <any> } or { id, ok: false, error: <string> }

- type: 'host.event'
  payload: { name: <string>, data: <any> }

- type: 'host.req'
  payload: { id: <number>, method: <string>, args: <array> }

KeyEventObject format (normalized)
----------------------------------
{
  type: 'keydown'|'keyup'|'keypress',
  code: 'KeyA'|'ArrowLeft'|...  // KeyboardEvent.code
  key: 'a'|'A'|'Enter'|'ArrowLeft'|...
  altKey: boolean,
  ctrlKey: boolean,
  shiftKey: boolean,
  metaKey: boolean,
  repeat: boolean,
  timestamp: number   // high-resolution (performance.now())
}

rs232 permission model & hooks
------------------------------
- Every guest request goes through the permissionChecker before being executed.
- permissionChecker signature:
    async function(method, args, meta) => { allowed: boolean, reason?:string, requireUserGesture?:boolean }
- If permissionChecker returns allow=false and requireUserGesture=true, host UI should show an explicit consent modal to the user. Consent results must be audited.
- rs232 will deny requests that exceed configured rate limits or if guestOrigin is not trusted.

Rate-limiting & quotas
----------------------
rs232 enforces:
- maxCommandsPerSecond (config) per guest (sliding window).
- maxConcurrentRequests (config) outstanding host->guest requests.
- per-method limits can be added via permissionChecker.

Error handling
--------------
- Timeouts: if a guest request doesn't receive a host response within defaultTimeoutMs, rs232 rejects the request and logs audit.
- Malformed messages: messages without __qandy or without the expected shape are ignored and optionally logged.
- Untrusted origin: messages from non-matching origin are ignored (unless allowWildcardOrigin is true for dev).

Common host-handler return pattern
---------------------------------
handlers registered via rs232.onRequest should return one of:
- { ok: true, result: <any> }
- { ok: false, error: '<string>' }
If they throw, rs232 will catch and return { ok:false, error: String(err) }.

Example usage (host-side)
--------------------------
/* Initialize */
rs232.init({
  guestWindow: null,
  guestOrigin: 'https://guest.qandy.example',
  defaultTimeoutMs: 10000,
  maxCommandsPerSecond: 50,
  auditLogger: (action, details) => { console.log('AUDIT', action, details); }
});

/* connect an iframe when created */
rs232.connectGuest(guestIframe.contentWindow, 'https://guest.qandy.example');

/* register handlers for guest requests */
rs232.onRequest(async function (req) {
  const { id, method, args, meta } = req;
  if (method === 'dosSave') {
    // permission check via permissionChecker happens automatically
    try { await window.dosSave(args[0], args[1]); return { ok:true, result: true }; }
    catch (e) { return { ok:false, error: String(e) }; }
  }
  // return undefined to let other handlers run or to result in unknown-method
  return undefined;
});

/* forward a key event (called from qandy keyboard handler) */
const keyEv = { type:'keydown', code:'KeyA', key:'a', altKey:false, ctrlKey:false, shiftKey:false, metaKey:false, repeat:false, timestamp: performance.now() };
rs232.forwardKey(keyEv);

/* host -> guest request */
const runResult = await rs232.sendRequest('exec', ['console.log("hello");']);

/* revoke raw input */
rs232.revokeInputMode();

Guest integration (what guest should send)
------------------------------------------
- Guest sends requests as:
  parent.postMessage({ __qandy:true, type:'guest.req', payload:{ id: 123, method:'dosList', args: [] } }, parentOrigin);
- Guest expects host response 'host.res' with same id (ok/result or error).
- Guest receives events from host via 'host.event'.

Security recommendations (must follow)
-------------------------------------
1) Always configure guestOrigin explicitly in production. Do not use '*' in production.
2) Never allow direct guest access to host globals, storage or DirectoryHandles.
3) Require explicit user confirmation for:
   - granting 'raw' keyboard mode
   - mounting directories
   - uploading or downloading large files
4) Audit all privileged operations: mount/format/delete/upload/download, raw-mode grants.
5) Use permissionChecker to centralize policy decisions and prompts.
6) Do not forward sensitive key combos (Ctrl+W, F5, Ctrl+Shift+I, Alt+F4) to guest. rs232.forwardKey must filter them.

Testing checklist
-----------------
- Validate messages are only accepted from configured origin.
- Check request/response lifecycle, timeout behavior.
- Test permissionChecker prompts and confirm that guest requests are paused until resolution.
- Ensure auditLogger receives appropriate structured events: {ts, guestOrigin, method, argsSummary, result, userAction?}
- Test raw mode enable/disable plus escape hotkey or UI kill-switch.

Example audit entries (recommended format)
-----------------------------------------
{
  ts: "2026-02-27T12:34:56Z",
  actor: "guest",
  origin: "https://guest.qandy.example",
  action: "dosSave",
  args: { filename: "notes.txt", size: 1024 },
  result: "ok",
  userConsent: true
}

Extensibility notes
-------------------
- rs232 is transport-agnostic. If you add a WebSocket or native serial interface later, implement a small adapter that presents the same onRequest/sendRequest semantics and plug it into rs232.
- Keep permissionChecker lightweight and declarative. Use it to define uiPrompts for the user (title, reason, buttons).
- Consider providing a small test harness page (dev-only) that simulates guest messages to exercise rs232 handlers.

Versioning & compatibility
--------------------------
- Keep rs232 API stable. If changes are needed, bump a version constant inside rs232 and provide a migration shim.
- Avoid exposing internal Maps or mutable internals to guests.
