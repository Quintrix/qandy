     Punch card machines such as the UNIVAC were programmed by inserting 'plugs' into
     holes on a 'plug board'; the gfx.js sends a series of 'plugs' to qandyland.js where
     plugboard() processes them. All 'plugs' are two upper-case characters we call 'verbs'
     with two-character 'nouns' attached, the server will respond to the plugs with plugs
     so some of these plugs are client plugs sent to the server, and others are server plugs
     sent to the client: 

      Client:  Server:

           ST   ST<token> — request session token                 
       ID$$##             — Item $$ down (user has clicked item $$ on z-location ##)
       OD$$##             — Object $$ down (user has clicked object $$ on z-location ##)
                XX%%..    — Error %%
           LK   LK<data>  — Look Around (use LOS to see beyond current sector)
           RF   RF<data>  — Refresh current sector
                PI$$##    — Player has been assigned item $$ at ## z-location
                VA        — Server request for player avatar (triggers select avatar)
                S%..%S    — Server Plugs for gfx.js engine to pass on to client, these let
                            UNIVAC send plugs to gfx.js which sends them to client's serverdown()
                            function which gives developers access to the UNIVAC's results.

     The 'UNIVAC Punch Code Processor' emulates a binary coded decimal computer, but
     with a base of 36 instead of 10. It processes text files as if they were punch cards
     programmed via a 'plugboard' using a retro-future 'plug code' language similar to
     'short code' that was used on what would become the UNIVAC. It is composed of two-character
     words that we divide into 'nouns' (the items), the 'verbs' (game instructions), the
     'registers' which are the variables, and the 'logic gates' that do the math.
     
     Let's say a game designer needs 'hit points', so they assign 'Wh' to be hit points.
     The player file is it's 'inventory', if a player has the item Wh in their file they
     have 1 hit point. If they have 'WhWh', they have 2 hit points. 'WhWhWh' would be 3,
     or they can be stacked from 'Wh00' to 'Wh99'.
     
     XiLaVtA1YeXcXiLbVtH8ZeXc = if player's inventory (Xi) has 'black hat' (La) teleport (Vt)
     to sector A1's 'Ze' (teleport), clear gate (xc). if player's inventory (Xi) has 'blue hat'
     (Lb) teleport (Vt) to sector H8's 'Ze' (teleport), clear gate (Xc).
     
     Because there are no jumps/branches/goto/gosub these files are processed from
     start to finish just a like a punch card, where you can't just move the card in
     and out of the machine - it is read from the start to the finish and yields
     blinding fast processing speeds that combined with a RAM drive with no moving parts
     and tiny data packets allows for a massive multiplayer gaming environment. 

     Punch Codes start with an upper-case letter followed by a lower-case letter or a
     numeral. Codes that have two-capital letters are codes for the 'plugboard'. The
     plugboard() runs the player file through the UNIVAC() that processes the codes in
     the objects. So if you 'use well', the UNIVAC() will run the 'well' object's code
     and output a new player file, in this case replacing an empty bucket in the player's
     inventory with a bucket of water. Or it could be programmed to return 'nothing',
     game developers can write their own code for each and every object in the game.

     These codes allow .gfx developers to create any type of world they desire, where
     they can program a 'dumb server to do smart things'.   
      
     Legend:     $$ = byte code (Aa-Zz or A0-Z0)
                 $* = *wildcard (A*-Z*)
                 ## = numeral 00-99
                 
                 %% = text validated: A-Za-z0-9 !@#$%^&*()-+=;:?,."'
                 -- = used by some codes as quotes for --strings-- 
                      (some codes only use it as an end-quote to terminate the input)
                 
               (NA) = not implemented yet, code's purpose reserved

        W* Registers:
        
        There are two sets of registers that can be used as 'variables':

          W0-W9 — global, stored in the 'a' (alpha) file and used as the UNIVAC's 'memory', these
                  variables are global.
          
                   W0 — first spawn map sector, the 'lobby'
                   W1 — first byte of next unique player id
                   W2 — second byte of the next unique player id
                   W3-W9 — reserved for future use
     
          Wa-Wz — local, can be used by game developers for points, levels, quest flags, etc.
          
          W_-W@ - the 'illegal' registers named after the C64 registers that are not
                  documented but work because of the way the CPU was made. These registers
                  are valid extended city symbols that don't get saved in the player's
                  file so they can be used for temporary purposes: _()[]{}^,:;+-=%@

     Item ID Codes - the 'nouns' in the punchcode language, the first character will always
     be a capital letter, the second character is a lower-case letter or numeral.  The file
     gfx-itemid.js contains the master list of all ItemID codes, which can be edited using
     the 'gfx-mods.htm' stand-alone tool, which allows a developer to edit the master
     gfx-item.js file, or insert mods into a .gfx file that will only affect that particular
     .gfx game. It is recommend you add mods to your .gfx file so it remains compatiable with
     any server it is run on. 
     
     Items are sorted by the first character of their id:

       A — travel items
       B — tools
       C — items
       D — quest items
       E — stacked items
       F — ingredient
       G — plant based food
       H — baked food
       I — raw food 
       J — cooked food
       K — mining items
       L — hats and helms
       M — swords and shields
       N — unused
       O — unused
       P — unused
       Q — unused
       R — unused
       S — player items, will have an avatar attached
       T — buildings - images can be bigger than 32x32
       U — buildings - images can be bigger than 32x32 
       V — v-verbs (game commands)
       W — registers (variables)
       X — x-logic (logic gates)
       Y — server items that have punchcode
       Z — server items that have punchcode 

     ——————————————————————————————————————————————————————————————————————————————————————————

      Map sectors can run from 'Az' to 'Zz', the W4 register holds the lower bound
      map sector, the default used in capflag.js being 'Hh' which is eight sectors tall
      and eight sectors wide, the dimensions of a chess board. 
      
      If the second character of the map code is a numeral or symbol, it is considered an
      'extended city'. There are 26 valid symbols so each map has one extended city sector,
      using graphics and roleplay this can be 'up' with blue sky and clouds, or it can
      be 'down' as a dark dungeon or sewer giving the engine the illusion of three dimensions,
      the player is on a world map that can go either up or down.

      Symbol Order  = 0123456789%()+,-:;=[]^_{}@
      
      As a 'dumb server that can do smart things' the UNIVAC does not validate registers,
      thus there is room to expand the V$ W$ and X$ codes to use these symbols, in theory
      registers W% - W} are not used by the UNIVAC and DevTeam considers them 'illegal
      registers' in the context of Commodore 64's 'illegal oprends' that are not documented
      but just exist because of the way the hardware was made.

     The gfx-compiler.js can edit several server files, these one character filenames get
     saved in the qandyland.js RAM drive to be used by the UNIVAC():

       a — alpha, the UNIVAC()'s 'inventory' with config data
       b — before, executed before the player's 1-second tick
       c — after, executed after the player's 1-second tick
 
     UNIVAC() inventory file that can include these items:

       W0$$ — spawn new players on map $$  
       W1## — spawn new players on map z-location ##
       W2## — player id counter (1st bit)
       W3## — player id counter (2nd bit)

     Programming Clients:
     
     The gfx.js engine is designed to work with any type of game that wants to use
     the UNIVAC() to process data, in fact gfx.js by itself does nothing. To use 
     the engine, a developer must write a 'client.js', the capflag.js will be the
     flagship game of the 'multiplayer graphics engine' and can be used as a template.
     
     The gfx.js checks to see if certain functions have been defined, and if so sends
     data to them:
     
          objdown(code) — the player clicks an object (code = itemid + itemz, ie: Yj44)
         itemdown(code) — the player clicks an item (code = itemid + itemz, ie: Sa33)
       playerdown(code) — itemdown() sends clicks on 'player items' here
          invdown(code) — the player requests to see their inventory file
       serverdown(code) — the UNIVAC() sends punchcode here for direct client access
     keydown(key,event) — the Qandy sends virtual key press events here
